# Guía de estudio: modelo C4

Esta guía sirve para entender qué representa C4, elegir el nivel de detalle adecuado y crear diagramas que otras personas puedan leer sin que su autor tenga que explicarlos.

## 1. La idea en una frase

C4 es una forma de describir la arquitectura de software mediante vistas con distintos niveles de zoom: primero el sistema y su entorno, luego las aplicaciones y almacenes que lo componen, después sus componentes internos y, solo cuando hace falta, el código.

El nombre viene de sus cuatro niveles principales: **Context, Containers, Components, Code**. El modelo también incluye diagramas de apoyo para mostrar el panorama de varios sistemas, el orden de una interacción o dónde se ejecuta el software.

Piensa en un mapa: un mapa del país y un plano de una estación pueden describir el mismo lugar, pero responden preguntas distintas. En C4 también cambia la escala y la pregunta; no se trata de dibujar todos los niveles por obligación.

## 2. Para qué sirve

Un buen diagrama C4 ayuda a responder preguntas concretas, por ejemplo:

- ¿Qué sistema estamos describiendo y quién lo usa?
- ¿Con qué sistemas externos se comunica?
- ¿Qué aplicaciones desplegables y almacenes forman el sistema?
- ¿Qué responsabilidades tienen las partes importantes de una aplicación?
- ¿Qué pasos ocurren en un flujo crítico?
- ¿En qué entorno y nodos se ejecuta cada parte?

C4 no decide si una arquitectura es buena ni prescribe una tecnología, un estilo arquitectónico o una notación gráfica. Es un marco para comunicar estructura y relaciones. La calidad depende de que el alcance, los elementos, las conexiones y el vocabulario sean claros.

## 3. El ejemplo que usaremos

Imagina **CitaSalud**, una plataforma que permite a pacientes reservar citas médicas. El sistema recibe solicitudes desde una aplicación web, consulta disponibilidad en su base de datos, envía confirmaciones por correo mediante un proveedor externo y permite al personal de la clínica administrar la agenda.

Usaremos el mismo sistema en los niveles siguientes para ver cómo cambia el zoom. Los nombres y tecnologías del ejemplo son ilustrativos.

## 4. Los cuatro niveles principales

| Nivel | Qué representa | Pregunta que responde | Qué suele incluir | Audiencia típica |
|---|---|---|---|---|
| **1. Contexto del sistema** | El sistema completo como una unidad y su entorno | ¿Quién usa el sistema y con qué otros sistemas se relaciona? | Personas, sistema de interés, sistemas externos y relaciones | Negocio, producto, desarrollo, operaciones |
| **2. Contenedores** | Las aplicaciones y almacenes de datos desplegables que forman el sistema | ¿Cuáles son las piezas ejecutables o desplegables y cómo se comunican? | Aplicación web, API, base de datos, worker, colas | Equipos técnicos y partes interesadas que necesitan entender la solución |
| **3. Componentes** | La organización interna de un contenedor seleccionado | ¿Qué responsabilidades principales hay dentro de esta aplicación? | Componentes con responsabilidades y relaciones | Equipo que diseña o mantiene esa parte |
| **4. Código** | Detalles de implementación de un componente | ¿Cómo está implementada internamente esta pieza? | Clases, interfaces, módulos u otras estructuras de código | Desarrolladores que trabajan en esa implementación |

Los diagramas de **contexto** y **contenedores** suelen bastar para la mayoría de los equipos. Baja a componentes o código solo si ese detalle aclara una decisión, una responsabilidad o un problema real. El diagrama de código suele ser innecesario o puede generarse desde el IDE cuando se necesita temporalmente.

### 4.1 Contexto del sistema

El sistema de interés aparece como una sola caja. Alrededor se muestran las personas y los sistemas externos que interactúan directamente con él. El límite del sistema debe ser evidente.

Para CitaSalud, un contexto podría mostrar:

- **Paciente**, que reserva o cancela una cita.
- **Personal de clínica**, que administra la agenda.
- **CitaSalud**, el sistema que estamos describiendo.
- **Proveedor de correo**, sistema externo que envía notificaciones.

No incluyas aquí bases de datos, microservicios internos, clases ni detalles de infraestructura: pertenecen a niveles más detallados. Si necesitas mostrar el contexto de muchos sistemas de una organización, considera un **System Landscape**.

### 4.2 Contenedores

En C4, un **contenedor** es una aplicación o almacén de datos que se ejecuta como una unidad y tiene una responsabilidad clara. Puede ser una aplicación web, una API, un servicio, una aplicación móvil, una base de datos o una cola.

**No significa necesariamente un contenedor Docker.** Docker puede ser la tecnología con la que se empaqueta un contenedor C4, pero no define el término.

Para CitaSalud podríamos mostrar:

- **Aplicación web**: interfaz usada por pacientes y personal.
- **API de citas**: aplica reglas de reserva y expone operaciones a la web.
- **Base de datos de citas**: conserva pacientes, disponibilidad y reservas.
- **Worker de notificaciones**: procesa solicitudes de correo.

Este diagrama muestra las principales piezas ejecutables y sus comunicaciones, no cada biblioteca, función, tabla o endpoint. Añade tecnologías cuando ayuden a entender o tomar decisiones; no conviertas el diagrama en una lista de marcas.

### 4.3 Componentes

Un componente agrupa una responsabilidad significativa **dentro de un contenedor**. En el ejemplo, dentro de la API podrían existir:

- **Controlador de citas**: recibe las solicitudes de reserva.
- **Servicio de disponibilidad**: comprueba horarios libres.
- **Servicio de reservas**: confirma y cancela citas.
- **Repositorio de citas**: lee y escribe los datos necesarios.

El componente no es automáticamente una clase, un microservicio ni un módulo del framework. Es una pieza arquitectónica cuya responsabilidad merece explicarse. Si las cajas solo repiten nombres de clases o no ayudan a comprender el diseño, probablemente este nivel no aporta valor.

### 4.4 Código

El nivel de código explica la implementación interna de un componente: por ejemplo, las clases principales y sus relaciones. Es un zoom opcional y de vida corta: el código cambia con frecuencia, así que mantener un diagrama manual puede ser costoso.

Usa este nivel si aporta valor a una revisión o explicación específica. Para muchas preguntas de diseño, el código fuente, los diagramas generados o una prueba ejecutable son una referencia más fiel.

## 5. Diagramas de apoyo

No son niveles adicionales de zoom equivalentes a los cuatro anteriores; responden a otros tipos de preguntas.

| Diagrama | Pregunta | Ejemplo para CitaSalud |
|---|---|---|
| **System Landscape** | ¿Qué sistemas hay en un entorno u organización y cómo se relacionan? | CitaSalud junto a facturación, identidad y otros sistemas clínicos |
| **Dynamic** | ¿Qué colaboración y orden de pasos ocurre en un escenario? | Paciente reserva una cita, se comprueba disponibilidad y se programa una confirmación |
| **Deployment** | ¿En qué nodos o entornos se ejecuta el software? | Aplicación web en CDN, API en nodos de nube y base de datos administrada |

Un diagrama dinámico puede enfocarse en un sistema o en un contenedor y es útil para explicar un flujo. Uno de despliegue relaciona instancias desplegadas con la infraestructura que las aloja. Si necesitas representar secuencias complejas, protocolos, decisiones o estados con precisión, una notación especializada como UML puede ser más adecuada.

## 6. Ejemplo de lectura: reserva de una cita

Desde el contexto, el paciente solicita una reserva a CitaSalud y el sistema solicita el envío de una confirmación al proveedor de correo.

Al hacer zoom al nivel de contenedores, podemos explicar la ruta técnica:

1. La **Aplicación web** envía la solicitud a la **API de citas** por HTTPS.
2. La API comprueba la disponibilidad y guarda la reserva en la **Base de datos de citas**.
3. La API envía una solicitud de notificación al **Worker de notificaciones**.
4. El worker solicita al **Proveedor de correo** enviar la confirmación.

En un Dynamic Diagram, mostraríamos el orden de estas interacciones para un escenario específico; en un Container Diagram, mostraríamos las piezas y sus relaciones sin detallar cada ejecución paso a paso.

## 7. Cómo elegir el diagrama

Empieza por la pregunta del lector, no por la herramienta ni por el diagrama que te resulte más vistoso:

1. **¿No queda claro el límite o el entorno del sistema?** Haz un System Context.
2. **¿Se necesita entender cómo está formada la solución?** Haz un Container Diagram.
3. **¿Hay una parte interna difícil de explicar?** Considera un Component Diagram de ese contenedor.
4. **¿La pregunta trata sobre el orden de un escenario?** Haz un Dynamic Diagram.
5. **¿La pregunta trata sobre dónde se ejecuta el software?** Haz un Deployment Diagram.
6. **¿Ninguna decisión o conversación mejora con el diagrama?** No lo crees o retíralo.

Es normal que una documentación tenga solo dos diagramas C4. La regla es usar el mínimo zoom que responda bien la pregunta.

## 8. Reglas para que el diagrama se entienda

El modelo es independiente de la notación. Puedes usar cajas y flechas, UML, una herramienta visual o texto como Mermaid; C4 no obliga a usar una sintaxis concreta. Sea cual sea la herramienta:

- Pon un **título** con el tipo y el alcance: “Container Diagram de CitaSalud”.
- Explica la **notación**: significado de formas, colores, flechas y líneas.
- Identifica el **tipo** de cada elemento: persona, sistema, contenedor o componente.
- Añade una **responsabilidad breve** a cada elemento.
- Incluye la **tecnología** de contenedores y componentes cuando sea pertinente.
- Dibuja cada relación en una dirección y etiqueta la línea con la intención; evita “usa” sin más contexto.
- Indica protocolo o mecanismo en comunicaciones entre contenedores, cuando sea relevante (por ejemplo, HTTPS, SQL o una cola).
- Mantén los mismos nombres y límites entre diagramas relacionados.
- Explica siglas y abreviaturas; no uses el color como único portador de significado.
- Comprueba que el diagrama puede entenderse, en gran parte, sin una explicación oral.

El color, la forma, el grosor de la línea y la disposición no tienen significados universales en C4: si los usas con significado, inclúyelo en la leyenda.

## 9. Errores frecuentes y cómo corregirlos

| Problema | Por qué confunde | Cómo mejorarlo |
|---|---|---|
| Llamar “contenedor” únicamente a un Docker container | Mezcla el concepto C4 con una tecnología de empaquetado | Describe aplicaciones y almacenes desplegables, con o sin Docker |
| Poner base de datos y clases en el contexto | Combina niveles de zoom | En contexto, muestra el sistema como una unidad y su entorno |
| Mostrar cada microservicio, tabla o biblioteca en un solo diagrama | Oculta las relaciones importantes | Reduce el alcance o crea una vista más detallada aparte |
| Flechas sin etiquetas o etiquetas como “usa” | No queda claro qué flujo o dependencia representa | Especifica la acción y dirección: “consulta disponibilidad por HTTPS” |
| Caja sin nombre de tipo o responsabilidad | El lector debe adivinar qué es y para qué sirve | Añade tipo y una descripción corta |
| Diagrama que mezcla estado actual y futuro | Las personas pueden confundir una propuesta con la realidad | Titula el estado y la fecha o versión representada |
| Crear los cuatro niveles por cumplir una lista | Genera detalle sin una pregunta que lo justifique | Añade solo vistas que ayuden a una audiencia concreta |
| Diagrama bonito pero ambiguo | La apariencia no aclara los límites ni las relaciones | Valida con la lista de revisión oficial y con un lector ajeno al dibujo |

## 10. Método de trabajo recomendado

1. **Define propósito y audiencia.** Escribe qué decisión, conversación o explicación debe apoyar el diagrama y quién lo leerá.
2. **Fija el alcance.** Nombra el sistema, el entorno y qué queda dentro y fuera.
3. **Empieza por contexto.** Identifica personas y sistemas externos que interactúan con él.
4. **Haz zoom a contenedores.** Añade aplicaciones, almacenes de datos y relaciones de comunicación.
5. **Añade detalle bajo demanda.** Crea vistas de componentes, dinámicas o despliegue solo para preguntas concretas.
6. **Usa nombres precisos.** Cada flecha debe explicar quién inicia la relación, qué hace y, cuando conviene, mediante qué tecnología.
7. **Revisa con otra persona.** Pídele que explique el diagrama sin ayuda; apunta dónde duda.
8. **Verifica y mantén.** Contrasta la vista con el sistema real y actualízala cuando cambien límites o relaciones arquitectónicamente relevantes.

## 11. Lista breve de revisión

Antes de compartir un diagrama, verifica:

- [ ] El título indica el tipo de diagrama y su alcance.
- [ ] El nivel de zoom es coherente; los elementos pertenecen a ese nivel.
- [ ] El límite del sistema y los elementos externos son claros.
- [ ] Cada caja tiene nombre, tipo y responsabilidad comprensibles.
- [ ] Las flechas tienen dirección y describen la relación.
- [ ] Se entienden las tecnologías y protocolos importantes.
- [ ] Siglas, colores, formas e iconos están explicados.
- [ ] No hay detalles que distraen de la pregunta del diagrama.
- [ ] Una persona que no lo creó puede entenderlo sin una explicación larga.

La [lista oficial de revisión](https://c4model.com/diagrams/checklist) desarrolla estos puntos.

## 12. Preguntas para comprobar comprensión

Intenta responder sin mirar las secciones anteriores:

1. ¿Qué representa un contenedor C4? ¿Por qué no es sinónimo de Docker?
2. ¿Qué elementos esperarías encontrar en un diagrama de contexto y cuáles dejarías para contenedores?
3. ¿Qué pregunta responde un Component Diagram que no responde uno de contenedores?
4. Si quieres explicar los pasos de una reserva, ¿qué diagrama elegirías? ¿Y si quieres mostrar los nodos donde se ejecuta la API?
5. ¿Qué información debería acompañar una flecha entre dos contenedores?
6. ¿Por qué no siempre conviene crear los cuatro niveles?

**Respuestas orientativas:** el contenedor es una aplicación o almacén de datos ejecutable/desplegable; el contexto muestra personas y sistemas alrededor del sistema de interés; los componentes explican responsabilidades internas de un contenedor; Dynamic explica interacciones ordenadas y Deployment la ejecución en infraestructura; las flechas deben expresar intención, dirección y, cuando aporta valor, protocolo; cada vista debe resolver una pregunta real.

## 13. Ruta de estudio y laboratorio

Una secuencia útil para estudiar es:

1. Leer el [modelo C4 oficial](https://c4model.com/) y las páginas de [abstracciones](https://c4model.com/abstractions).
2. Comparar los [diagramas](https://c4model.com/diagrams), empezando por contexto y contenedores.
3. Revisar [notación](https://c4model.com/diagrams/notation) y la [lista oficial de revisión](https://c4model.com/diagrams/checklist).
4. Aplicar estas ideas al [Laboratorio 01 — C4](../labs/01-c4.md): modela un sistema conocido, crea contexto y contenedores, y añade despliegue y un diagrama dinámico para una necesidad concreta.
5. Explorar una herramienta después de entender el modelo: [Structurizr](https://docs.structurizr.com/), [Structurizr DSL](https://docs.structurizr.com/dsl) o [C4-PlantUML](https://github.com/plantuml-stdlib/C4-PlantUML).

Las herramientas ayudan a producir y mantener diagramas, pero no corrigen límites confusos ni relaciones mal explicadas.
